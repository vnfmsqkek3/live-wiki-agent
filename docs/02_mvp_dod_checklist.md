# Living Wiki MVP 완료 정의(DoD) · 데모 체크리스트

> 원본: `공통문서/Living_Wiki_MVP_DoD_Demo_Scenarios.pdf` (6p) — 기능 구현 완료 정의(DoD) 및 해커톤 데모 시나리오 · 실데이터 미사용 · 합성 데이터 기반 · AWS MVP 실행 계획
> 용도: 기능 완료 판정, QA 기준치, 최종 데모 리허설. **P0가 모두 체크되어야 MVP 완료.**
> 다른 문서와 충돌하면 범위·완료 기준은 이 문서가 우선한다 (예: 설계서의 "7분 데모"·"4주 일정"은 이 문서의 12분 데모와 팀 계획 일정으로 대체).

핵심 메시지: **문서를 저장하는 Wiki가 아니라, 지식의 신뢰성과 유효성을 관리하는 Wiki.**

| 엔진 | 역할 |
|---|---|
| Trust Gate | 위조·악성·규정 충돌 문서의 무검증 게시 방지 |
| Knowledge Validation | 기반 데이터로 노하우의 적용 조건과 충돌 여부 검증 |
| Change Impact | 기반 규정 변경 시 관련 노하우 재검증 |
| Trust-aware Search | 승인된 지식의 근거·시행일·신뢰 상태 제시 |
| Agent Governance | 승인 권한 강제 및 정답 데이터 기반 품질 평가 |

---

## 1. 완료 판정 원칙

- 화면 노출만으로 완료 처리하지 않는다. **입력 → 판단 → 통제 → 결과 → 검증 근거**가 연결되어야 한다.
- P0: 데모 전 실제 End-to-End 동작 필수. P1: 추가 차별화 항목. P2: 확장 검토.
- 테스트는 합성 데이터와 사전 정의한 Ground Truth로 **반복 실행 가능**해야 한다 (수작업 확인만으로 완료 처리 금지).
- 승인되지 않은 문서는 Knowledge Base의 사용자 검색 대상에서 제외되어야 한다.

## 5. 데모 구성 (12분)

추천 메인 스토리: 정상 노하우 등록 → 위조 문서 차단 → 규정 변경 → 기존 노하우 재검증 → 주니어의 최신 지식 검색

| 구간 | 시간 | 내용 | 증명 포인트 |
|---|---|---|---|
| 01 | 1분 | 문제 정의·메인 검색 | 저장보다 검증·최신성 |
| 02 | 2분 | 정상/위조/악성 문서 업로드 | Trust Gate 차단 |
| 03 | 2분 | 정상/충돌 노하우 검증 | 공식 근거와 비교 |
| 04 | 2분 | 규정 v1 → v2 개정 | 영향 문서 자동 탐지 |
| 05 | 3분 | 조문 검색·AI 실무 가이드 | 출처·시행일·검증 상태 |
| 06 | 2분 | 비인가 게시·평가 대시보드 | 권한 강제·품질 측정 |

### 5.1 단계별 실행 스크립트

**01. 서비스 소개 (1분)**
- [ ] 메인 검색 화면 표시
- [ ] 기존 Wiki의 위조·노후·규정 위반 문서 축적 문제 설명
- [ ] 기반 데이터 → 노하우 검증 → 변경 영향 관리의 연결 강조

**02. Trust Gate (2분)**
- [ ] F-001 업로드 → Registry 일치 → 승인
- [ ] F-003 업로드 → 공식 출처 불일치 → 게시 차단
- [ ] A-001 업로드 → Prompt Attack 검사 결과 확인
- [ ] 차단 문서가 일반 사용자 검색 결과에 없는지 확인

**03. 노하우 검증 (2분)**
- [ ] K-001 업로드 → 관련 규정 확인 → 승인
- [ ] K-002 업로드 → 필수 절차 누락 탐지
- [ ] 충돌 조문과 판단 근거 표시 → 게시 보류

**04. Change Impact (2분)**
- [ ] F-002 개정본 등록
- [ ] 개정 전후 Diff 표시
- [ ] K-001/K-003 등 관련 노하우 탐지
- [ ] 수정 초안 생성 → 승인 전 자동 게시 금지

**05. Trust-aware Search (3분)**
- [ ] 주니어 질문: "담보평가 시 확인 절차는?"
- [ ] 승인된 규정과 노하우를 함께 검색
- [ ] 제12조제2항제3호가목 계층 탐색
- [ ] 출처·시행일·검증 상태 제시
- [ ] 삭제/미확인 조항은 DELETED / UNVERIFIED로 구분

**06. Agent Governance (2분)**
- [ ] 일반 사용자로 게시 Tool 호출
- [ ] AgentCore Policy 또는 Backend 권한 검사에서 거부
- [ ] 거부 Trace 확인
- [ ] Evaluations 대시보드에서 검색·인용·보안 평가 결과 확인

데모에 필요한 계정: `user`(일반 사용자 = 작성자: 업로드·게시 요청·검색), `admin`(업로드·게시 요청도 가능 + 승인·반려·관리). 별도 규정 승인자 계정은 두지 않는다 (사용자 결정 11/20). admin(PLATFORM_OPERATOR)은 자기 문서도 승인할 수 있고 감사에 SELF_APPROVAL로 남는다 (사용자 결정 11/18). 데모는 user 업로드 → admin 승인. 역할 정의는 `01_architecture_spec.md` 3장.
