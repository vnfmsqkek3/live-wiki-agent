# 혁신금융서비스 아키텍처 원칙 · 구현 체크리스트

> 원본: `공통문서/혁신금융서비스 1차 신청 아키텍처.pdf` (11p) — HANA BANK 혁신금융서비스 1차 신청, 생성형 AI 업무 혁신 과제 아키텍처(과제 1~3), 1차 신청용 초안 2026.11
> 용도: 서비스 당선 시 혁신금융서비스 신청을 전제로, 구현이 지켜야 할 아키텍처 원칙.
> 원본은 과제 1~3(마이데이터 연금 상담, UX 화면 생성 AI, 리서치 보고서 에이전트) 기준이며 Living Wiki는 원본에 없다.
> **적용 범위: 1~3장(공통 원칙)은 Living Wiki에 그대로 적용, 4장(과제별)은 참고, 5장은 팀이 만든 Living Wiki 대응 체크리스트.**
> 조항 번호·특례 해당 여부는 원본에서도 "원문 및 준법 부서 확인 필요"로 표기되어 있다.

**공통 전제: 원천 DB 온프렘 유지 · 개인/신용정보는 AI(Bedrock)에 전달하지 않음**

## 1. 데이터 처리 원칙

개인정보는 은행 통제 영역(온프렘·S3 원본)에 두고, Bedrock에는 비식별 데이터만 보내 외부 SOTA 모델의 성능을 안전하게 활용한다.

| No | 적용 | 원칙 | 내용 |
|---|---|---|---|
| ① | 공통 | 개인정보 저장 위치 | 개인정보는 온프렘과 클라우드 S3 원본 버킷에만 저장. S3 원본 버킷은 KMS로 암호화하고 AI 실행 역할의 접근을 IAM으로 차단 |
| ② | 공통 | AI 모델 전달 금지 | 개인정보는 Bedrock(AI 모델)에 전달하지 않음. S3 → Bedrock 구간에 개인정보 차단선을 두고 Bedrock은 비식별 정제 데이터만 처리 |
| ③ | 공통 | 데이터 유형별 모델 리전 | 비개인정보만 활용하면 해외 리전 Bedrock 모델 사용 가능. 가명처리 정보를 활용하는 경우에만 국내(서울) 리전 모델로 한정 |
| ④ | 과제 1 | 연금 상담 · 개인정보 있음 | 마이데이터 조회와 연금 계산은 온프렘에서 수행. 국내 리전 모델에 실제 값 대신 변수명과 범주 값만 전달하고, 실제 값은 온프렘에서 결합해 고객에게 제공 |
| ⑤ | 과제 3 | 리서치 · 개인정보 혼입 가능 | S3 원본 문서에서 개인정보를 찾아 마스킹. 마스킹할 수 없거나 판단이 불확실하면 차단. 통과한 비개인 문서만 정제 버킷을 거쳐 Bedrock에 전달 (해외 리전 모델 활용 가능) |
| ⑥ | 과제 2 | UX 화면 생성 · 개인정보 없음 | 입력은 디자인 에셋과 더미 데이터 화면으로 한정해 해외 리전 모델 활용 가능. 개인정보 스캔으로 혼입 여부를 검증하고 발견되면 차단 |

Living Wiki는 업로드 문서에 개인정보가 섞일 수 있으므로 **⑤(과제 3)와 같은 유형**이다.

## 2. 공통 아키텍처

### 2.1 온프렘 DB + S3 반출 게이트

```
[온프렘 (하나은행)]                  [특례 요청 구간]                    [AWS (모델 리전은 데이터 유형별 선택)]
 원천 DB                            · 반출 결재·로그                     Storage: S3 원본 버킷 ─────────▶ Security: 비식별 처리
 업무 단말 · 사용자        ───▶      · Direct Connect / PrivateLink  ───▶  (개인정보 포함 가능,              (Lambda · Step Functions,
 반출 게이트                         · 보완 통제: 승인 데이터 반출            KMS · AI 역할 접근 차단)          PII 탐지 → 마스킹·치환)
 결과 회수 저장소                      + AI 결과 회수만 허용                                                        │
                                                                   ─────── ▼ 개인정보 차단선 (AI는 비식별만) ───────
                                                                    AgentCore Agent ──▶ Bedrock KB ──▶ Neptune
                                                                    (AgentCore,          (정제 버킷 기반   (Analytics,
                                                                     Bedrock 모델)        벡터 RAG)         GraphRAG)
```

- S3 원본에는 개인정보가 있을 수 있지만, Bedrock·Knowledge Bases·Neptune은 비식별 처리를 거친 **정제 버킷 데이터만** 쓴다 (IAM 원본 접근 차단 + Guardrails).
- 비개인정보는 해외 리전 모델도 사용할 수 있고, 가명처리 정보는 국내(서울) 리전 모델로만 처리한다.

### 2.2 3계층 아키텍처 — 개인정보는 LLM Layer에 도달하지 않음

| 계층 | 구성 요소 | 역할 |
|---|---|---|
| Tier 1 · Agent Layer | Agent (AgentCore) | 요청 분류 · 도구 호출 |
| | AgentCore Runtime | Agent 실행 · 세션 격리 |
| Tier 2 · LLM Layer | Bedrock SOTA 모델 | 가명정보: 국내 리전 · 비개인: 해외 가능 |
| | Bedrock Guardrails | 입출력 PII · 범위 밖 응답 차단 |
| Tier 3 · Tool (MCP) Layer | Bedrock KB · Neptune | S3 정제 데이터 → 벡터 · GraphRAG |
| | AgentCore Gateway | MCP → Lambda → 온프렘 API |
| 개인정보 차단선 바깥 | S3 원본 버킷 | 개인정보 포함 가능, KMS · AI 역할 접근 차단 |
| | 온프렘 원천 DB | 마이데이터 · 계산 엔진, 실제 값 결합 |

- LLM Layer(Bedrock)에는 비식별 데이터와 변수명만 도달하고, 실제 개인정보는 Tool Layer 뒤(온프렘·S3 원본)에 남는다.
- 모델은 LLM Layer에서 교체할 수 있게 분리해, 모델 변경 시 영향 범위를 LLM Layer로 한정한다.

|---|---|---|---|
| 특례 요청 | 전자금융감독규정 제15조 (망분리) | 과제 1 · 3 · 2 | 공통 특례: 내부망 ↔ Bedrock 연결 허용 (Direct Connect · PrivateLink) |
| 특례 요청 | 신용정보법 제40조의2 (가명정보) | 과제 1 | 상담 목적 활용 시에만 해당. 실제 값은 온프렘에 두고 변수명·범주 값만 전달 |
| 현행 준수 | 전자금융감독규정 클라우드 이용 조항 | 공통 | 클라우드 안전성 평가·보고 절차 이행, 가명정보는 국내 리전 처리, KMS 암호화 |

| 현행 준수 | 금융소비자보호법 | 과제 1 | 상담 범위 제한, 고지문, Agent 답변 검증 |

## 4. 과제별 아키텍처 (참고)

### 4.1 과제 1 · 마이데이터 연금 상담 — 치환자 방식

| 영역 | 단계 | 내용 |
|---|---|---|
| 온프렘 (고객 실제 값은 여기에만) | ① PII 탐지·제거 | 고객 질문에서 개인을 식별하는 값(주민·외국인등록·여권·운전면허번호, 계좌·카드·전화·이메일·고객번호) 제거. 이름·나이 등 단독으로 개인을 식별하지 않는 값은 대상 아님 (사용자 결정 11/17) |
| | ② 마이데이터·연금 계산 | 원천 DB 조회·수령액 계산, 값은 온프렘 보관 |
| | ⑤ 결합기 → 고객 응답 | AI가 만든 답변 틀에 실제 값을 채워 고객에게 보여줌 |
| AWS 서울 리전 (고객 실제 값 없음) | ③ Agent · AgentCore Runtime | 변수가 들어간 답변 틀 생성 (Bedrock) |
| | ④ Bedrock Guardrails · Review | 입출력 PII·투자권유·범위 밖 차단, 근거 대조 |
| | ⑥ Bedrock Knowledge Bases | 연금 상품·약관 RAG |
| | ⑦ Neptune Analytics | 상품-세제-규정 그래프 |

- 흐름: 온프렘 → (변수명·범주만) → AWS → (답변 틀만) → 온프렘 결합기.
- 예) 보내는 것: `"{연금잔액} 기준 {예상수령액}을 설명" + 50대·중립형` → 받는 것: `"현재 {연금잔액}으로 월 {예상수령액}을 받을 수 있습니다"`
- 클라우드에는 고객의 실제 값·식별자가 한 번도 올라가지 않는다.

| 규제 이슈 | 관련 규정 (예상·확인 필요) | 보완 통제 |
|---|---|---|
| 망분리 예외 | 전자금융감독규정 (망분리) | 전용선·PrivateLink, 서울 리전, 접근통제·MFA |
| 개인신용정보 처리 | 신용정보법 · 개인정보보호법 | 치환자 방식(실제 값 미전달), S3→Bedrock 구간 비식별 처리·Guardrails |
| 재식별 위험 | 가명·익명처리 가이드라인 | 범주를 넓게 구간화(k-익명성), 식별자 미전달 |
| 투자권유 규제 | 금융소비자보호법 | Guardrails, 고지문, 상담 범위 제한 |
| AI 오답 | 금융분야 AI 가이드라인 | Agent 답변 근거 대조, 로그 보관 |

요지: 원천·계산은 온프렘, Bedrock에는 변수명과 범주형 속성만 전달.

### 4.2 과제 2 · UX 화면 생성 AI

| 영역 | 구성 | 내용 |
|---|---|---|
| 온프렘 | 디자인 자산, 현업 요청, 반출 게이트, 개발 반영 | |
| 특례 요청 구간 | 반출 결재·로그, Direct Connect / PrivateLink | |
| AWS Storage | S3 원본 버킷 | 디자인 토큰·컴포넌트 명세, 더미 데이터 화면만 |
| AWS Security | PII 스캔 검증 | 혼입 여부 자동 검증, 발견 시 차단·반려 |
| 차단선 이후 | AgentCore Agent → Bedrock KB → Neptune | Agent: AgentCore Browser 점검 / KB: UI 패턴 RAG, 가이드 문서 / Neptune: 화면-컴포넌트-토큰 관계 |

- 입력은 디자인 자산과 더미 데이터 화면으로 한정한다 (운영 화면 캡처 미사용). PII 스캔을 통과한 자료만 AI에 전달한다.
- 산출물(기획서·디자인·퍼블리싱)은 사람이 검토한 뒤 온프렘 개발에 반영한다.

| 규제 이슈 | 관련 규정 (예상·확인 필요) | 보완 통제 |
|---|---|---|
| 업무용 생성형 AI 사용 | 전자금융감독규정 (망분리) | 전용 연결, 접근통제, 사용자 인증 |
| 개인정보 혼입 | 개인정보보호법 | 입력을 디자인 자산·더미 화면으로 한정, PII 스캔 검증 후 발견 시 차단 |
| 설계자료 유출 | 전자금융감독규정 (정보보호) | 입력 데이터 학습 미사용, KMS 암호화, 로그 |
| 결과물 품질 | 내부 개발 표준 | 규칙 점검 + 사람 검토 후 반영 |

요지: 핵심 특례는 망분리(내부망 ↔ Bedrock 연결), 개인정보는 입력 단계에서 배제.

### 4.3 과제 3 · 리서치 보고서 에이전트 (Living Wiki와 가장 유사)

| 영역 | 구성 | 내용 |
|---|---|---|
| 온프렘 | 내부 문서(공개 등급), 보고서 템플릿, 반출 게이트, 결과 회수 | |
| 특례 요청 구간 | 반출 결재·문서 등급 확인, Direct Connect / PrivateLink | |
| AWS Storage | S3 원본 버킷 | 내부 문서·템플릿, 개인정보 포함 가능 |
| AWS Security | 비식별 처리 | 문서 PII 탐지·마스킹 → 정제 버킷 · KB 동기화 |
| 인터넷 | 허용 도메인만 (특례) | 비식별 처리 영역과 연결 |
| 차단선 이후 | AgentCore Agent → Bedrock KB → Neptune | Agent: AgentCore Fargate 렌더 / KB: 정제 문서 RAG, 문장별 출처 ID / Neptune: 기업·이슈·출처 관계 그래프 |

- 외부 웹검색에는 검색어만 보내고 내부 문서 원문은 보내지 않는다. 허용목록 프록시를 거친다.
- (사용자 결정 11/18, 참조 확인 단계) 검색 결과 도메인은 **전부 허용**한다. 대신 ① 검색어만 외부로 보내고 문서 원문·내부 정보(IP·사내 시스템명·사람 이름·내부 경로)가 든 검색어는 보내지 않는다 ② 웹페이지 글은 자료로만 다루고 지시로 따르지 않는다 ③ 결과는 "확인할 것" 제안일 뿐 자동 반영·근거 인용하지 않는다 ④ 검색어·열어 본 URL·결과를 감사 기록에 남긴다. 실제 은행 망분리 환경에서는 허용목록 프록시로 되돌려야 한다(MVP 시연 범위 한정).
- 문서 속 개인정보는 S3→Bedrock 구간에서 탐지·마스킹한 뒤에만 AI에 전달한다.
- (사용자 결정 11/18, MVP 한정) 관리자(PLATFORM_OPERATOR)는 자기가 올린 문서를 스스로 승인할 수 있다. 일반 결재자의 자기 승인은 계속 금지. 관리자 자기 승인은 `approvals.self_approved=true`·감사 `SELF_APPROVAL` 로 구분한다. 실제 운영에서는 되돌린다(마이그레이션 008).

| 규제 이슈 | 관련 규정 (예상·확인 필요) | 보완 통제 |
|---|---|---|
| AI의 인터넷 접근 | 전자금융감독규정 (망분리) | 허용목록 프록시, 검색어만 외부로 전송 |
| 내부자료 유출 | 전자금융감독규정 (정보보호) | 원본 버킷 AI 접근 차단(IAM), 문서 원문 외부 미전송, 학습 미사용 |
| 개인정보 혼입 | 개인정보보호법 · 신용정보법 | S3→Bedrock 전 PII 탐지·마스킹, Guardrails |
| 출처 신뢰성 | 내부 보고 기준 | 문장별 출처 ID, Reviewer 검증 |

요지: S3 원본의 개인정보는 비식별 처리 후에만 Bedrock에 전달.
