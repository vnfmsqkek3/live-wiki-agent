## Platform

## Users

- **은행 실무자** (영업점·본부 직원, 계정 '사용자'): 업무 중 기준이 필요할 때 규정·노하우·매뉴얼을 검색하고, 근거 조문과 시행일을 확인한 뒤 업무에 쓴다. 자기 노하우·매뉴얼을 올려 게시를 요청한다.
- **결재자·관리자** (계정 '관리자'): 결재함에서 게시 승인·반려, 공식 원본과 다른 문서의 출처 검토, 자동 차단 사유 확인을 한다.
- **1차 관람자: 하나은행 공모전 심사(시연)**. 당장은 심사 시연에서 위 두 흐름(찾아 쓰기, 올려 승인받기)을 짧은 시간에 보여 주는 것이 1차 목적이다 (사용자 확인 2026-11-17). 마감 2026-12-03.

## Product Purpose

금융기관 내부 지식(공식 규정·실무 노하우·매뉴얼)을 믿고 쓸 수 있게 관리하는 위키. 올라온 문서를 AI가 보안·개인정보·공식 원본 대조·규정 충돌까지 검사하지만 게시는 사람이 승인하고, 모든 지식을 근거 조문·시행일로 연결한다. 규정이 개정되면 그 규정을 근거로 쓴 노하우·매뉴얼을 재검토 대상으로 표시한다. 성공 = 실무자가 "이 문서를 믿어도 되는지, 무엇을 해야 하는지"를 바로 알고, 결재자가 무엇이 왜 문제인지 바로 판단하는 것.

## Positioning

두 축을 같은 무게로 (사용자 확인):
1. **AI가 검사하고 사람이 승인하며, 모든 지식이 근거 조문으로 연결된다.** 위조로 단정하지 않는다("위조 확정 아님, 출처 확인 필요").
2. **규정 개정 영향 추적.** 개정·삭제된 규정을 근거로 쓴 문서는 자동으로 재검토 대상이 되고, 무엇이 바뀌었는지 조문 단위로 보여 준다.

## Operating Context

- 데이터는 모두 **가상 하나은행 데이터(SYNTHETIC)**. 실제 하나은행 규정·고객정보가 아니며 모든 화면에 고지한다.
- 문서 흐름: 등록(PDF·DOCX·HWPX·PNG·JPG) → 자동 검사(악성코드·파일 구조·문자 인식·개인정보 가림·지시문 검사·분류·근거 대조) → 작성자 검토 → 게시 요청 → 관리자 승인 → 게시·색인 → 검색·보관함·업무 가이드.
- 신뢰 상태: 공식 규정 / 검증 완료 / 검토 필요(재검토) / 미검증. 같은 규정의 개정본은 한 문서(버전)로 묶이고 오늘 시행 중인 판이 대표.
- 상세에서 고칠 곳(밑줄)은 원본 내용·근거 내용·수정 내용 세 칸으로 보인다.

## Capabilities and Constraints

- Next.js 16 웹 (`apps/web`), API는 `apps/api` (Hono). 화면은 API 계약(`app/lib/api.ts`)을 바꾸지 않는다.
- 계정 2종(관리자·사용자), 권한 분기 `app/lib/roles.ts`.
- QA 스크립트(`tests/e2e/qa-flow.mjs`, `qa-admin.mjs`)가 화면을 실제로 조작해 점검한다. 선택자를 바꾸면 스크립트도 함께 바꾼다.
- 한국어 UI. 내부 코드·영문 상태값을 화면에 내지 않는다.
- 새 npm 의존성은 버전 고정 규칙(`docs/interfaces.md` 8장)을 따른다.

## Product Principles

1. 믿을 수 있는지가 먼저 보인다: 신뢰 상태·근거·시행일이 내용보다 앞선다.
2. 사람이 결정한다: AI 판정은 근거와 함께 제안으로 보이고, 승인·반려는 사람이 한다. 단정하지 않는다.
3. 궁금한 것만 열어 본다: 기본 화면은 짧게, 자세한 근거는 사용자가 골라 연다.
4. 바뀐 것을 놓치지 않는다: 개정·충돌·재검토는 눈에 띄게, 무엇이 어떻게 바뀌었는지까지.
